# tblBulkRunSchedule rationalisation

## What this is

Historically every client-specific schedule was a private copy: the same run
("AKL > HLZ Pre 8am Medical Run", Mon-Fri, same times, same speed, same depot)
exists once per client, so 21 clients means 105 identical rows. Kevin has added
a schedule/client link table so one schedule can serve many clients. This work
takes the current table, finds the copies, and produces:

1. the **link-table rows** (`ScheduleName, ClientId, CreatedUtc, CreatedBy`)
2. the list of **surviving** and **retired** `BulkRunScheduleId`s
3. a **SQL Server script** that applies it inside a transaction (rolls back by default)
4. a **staging apply** that converts *every* client schedule, switches off the
   legacy 1-1 `ClientId` path, and can be fully restored (section 7)
5. an **assessment of the name-keyed 1-many design** (section 5) — it is not
   robust as it stands, and the data shows exactly why.

Everything is generated by `rationalise_schedules.py` from a CSV export of the
sheet, so it can be re-run against a fresh export before applying.

## 1. Rules used

- A **schedule** is the set of day rows that share `Name` + `ClientId`
  (one row per `DayOfWeek`).
- Names are compared **case-insensitively with whitespace collapsed**
  (`Hamilton  > BOP` == `Hamilton > BOP`). The most common spelling wins.
- Two client schedules are **the same schedule** when every day row matches on
  every column except `BulkRunScheduleId` and `ClientId`. Identical duplicate
  rows inside one schedule are ignored for the comparison.
- Same name + same definition + 2 or more clients → **one shared schedule**.
  The copy with the lowest `BulkRunScheduleId` survives unchanged (it keeps its
  original `ClientId`); every client in the group gets a link-table row; the
  other copies are retired. A client copy that is identical to the **default**
  of the same name is linked to the default and its copy retired.
- Same name + **different** definition → a **variant**. The default, or else
  the group with the most clients, keeps the name; the others are given a
  proposed `Name #2`, `#3` … because a name-keyed link table cannot tell them
  apart otherwise. Variants with a single client are left exactly as they are.
- **Default schedules** (`ClientId NULL`) are never renamed or retired.
- `--scope merged` (production proposal) applies the above. `--scope all`
  (staging) additionally converts every one-client schedule to a link row so
  the 1-1 path can be disabled — see section 7.

## 4. Data-quality findings (168, in `data_quality.csv`)

- **48 names exist both as a default schedule and as client schedules.** 24 of
  those client copies are identical to the default and could simply use it.
  The other 24 are different definitions under the same name.
- **41 schedules contain fully identical duplicate day rows** (e.g. client
  17732 "Monday 2 hour express" has 7 copies of the Monday row). These are
  harmless for the merge but should be de-duplicated.
- **31 schedules have several *different* rows for the same day** (different
  windows on one day). Legitimate, but it means Name + ClientId + DayOfWeek is
  not a key either.
- **3 names differ only by case/whitespace**, plus a few obvious typos
  (`Auckland Afternoonss`, `Simday 2 hour express`) that the script does not
  touch.

## 5. Is Kevin's 1-many link table robust?

**No — keying the link on `ScheduleName` is the weak point.** The rest of the
shape (`CreatedUtc`, `CreatedBy`) is fine but incomplete. Specifically:

1. **`Name` is not a key in `tblBulkRunSchedule`.** A schedule has no id of its
   own — its identity is implicit in (`Name`, `ClientId`) spread over 1..n day
   rows. Today 158 names map to more than one definition, and 48 names are
   also used by a default schedule. A link row `("AKL > CHCH Pre 10am Medical",
   16947)` cannot say *which* of the six definitions it means. The `#n`
   renames in this proposal are a workaround for that, not a fix.
2. **No referential integrity is possible.** SQL Server cannot put a foreign
   key on a name that is not unique, so nothing stops a link row pointing at a
   schedule that has been renamed or deleted. Renames happen: the sheet shows
   the `*15:00:00-17:00:00` time suffixes and the `ss`/`dd` typos being edited
   in place. Every rename silently detaches every client on that schedule.
3. **String matching is fragile.** `Hamilton  > BOP` vs `Hamilton > BOP` will
   not join (collation ignores case, not whitespace). Trailing spaces and NBSPs
   are invisible in the UI and break the join.
4. **Nothing prevents duplicates or dangling rows** in the link table as
   described (no unique constraint on (`ScheduleName`, `ClientId`), no
   `RemovedUtc`/`IsActive`, so a client cannot be taken off a schedule with an
   audit trail).
5. **Schedules have dependants that a name does not carry.** `BulkZoneSchedule`
   and `tblBulkScheduleLinehaul` hang off `ScheduleId` (a day row id). Two
   clients' copies can have identical `tblBulkRunSchedule` rows but different
   zone activations — this script cannot see that, which is why the SQL has a
   check that lists retired ids owning zone/linehaul rows and refuses to be
   committed until it returns nothing.
6. **Resolution rule is undefined.** With the survivor still carrying the first
   client's `ClientId`, the lookup for a linked client is "rows where Name =
   link.ScheduleName". With defaults also using names, and defaults meant to
   apply only when a client has no schedule of its own, the precedence
   (own copy > link > default) has to be explicit in the query.

### Recommendation

- Introduce a **schedule header** (`tblBulkRunScheduleGroup`: `ScheduleGroupId`
  identity, `Name`, `IsDefault`, timestamps) and add `ScheduleGroupId` FK to
  every `tblBulkRunSchedule` day row. Back-fill it from (`Name`, `ClientId`).
- Key the link table on **`ScheduleGroupId, ClientId`** with an FK to the
  header and a unique constraint on the pair. Keep `CreatedUtc`/`CreatedBy`,
  add `RemovedUtc`/`RemovedBy` (soft delete) — or delete plus an audit table.
- Enforce **unique `Name` per header** (not per day row), trimmed, so the UI
  can still show and search by name without the name being the key.
- Move `ClientId` off the day rows entirely once every client is linked; until
  then treat `ClientId` on the row as "legacy owner" only.
- If the name key has to stay for now: add a unique index on
  (`ScheduleName`, `ClientId`), a `CHECK (ScheduleName = LTRIM(RTRIM(ScheduleName)))`,
  and apply the `#n` renames so each name resolves to exactly one definition.

`merge_groups.csv` / the `MergedSchedules` sheet carry the survivor
`BulkRunScheduleId`s for every shared schedule, so switching the link rows from
name-keyed to id-keyed is a join, not a re-analysis.

## 6. Applying the merge (production proposal)

1. Re-export the sheet (or query the table) to CSV and re-run:
   `python3 scripts/schedule-rationalisation/rationalise_schedules.py schedules.csv --created-by <who> --link-table dbo.<KevinsTable>`
2. Review the `Variants` sheet and decide whether the 33 `#n` renames are
   acceptable (`@RenameVariants = 1`) or whether those groups wait for the
   id-keyed design (`= 0`, in which case those groups are left untouched).
3. Run the SQL with `@Commit = 0`; all three safety-check selects must be empty.
4. Set `@Commit = 1`.

`CreatedUtc` is the script run time and `CreatedBy` defaults to
`steve@urgent.co.nz`; both are parameters (`--created-utc`, `--created-by`).

## 7. Staging: apply everything and switch the 1-1 schedules off

`tblBulkRunSchedule` has no active/disabled flag, so "disable the 1-1
schedules" has to mean: every client reaches its schedule only through the
link table, and nothing is left for the legacy `ClientId` lookup to find.
`rationalise_schedules_staging.sql` (generated with `--scope all`) does that,
and is reversible:

| Step | What it does |
|---|---|
| 0 | Snapshots `tblBulkRunSchedule` and `BulkZoneSchedule` into `*_PreRationalise_20260908` tables |
| 1-2 | Retires the 2,433 duplicate rows and inserts **2,606 link rows** — one per client schedule, including the 1,980 one-client schedules |
| 3 | Applies all **355** `#n` renames so every surviving definition has a unique name (not optional in this mode) |
| 5 | Safety selects (retired ids exist, zone/linehaul dependants, ambiguous names) |
| 6 | Deletes the retired rows and (`@RetireDependants = 1`) their `BulkZoneSchedule` rows |
| 7 | `@DisableLegacyClientId = 1`: sets `ClientId = NULL` on the **8,162** surviving client rows |

After it commits, every row in `tblBulkRunSchedule` has `ClientId NULL`
(8,677 rows: 515 default + 8,162 formerly client-owned). A schedule is a
"default" if it has no link rows; every other schedule is reachable only via
`tblBulkRunScheduleClient`. That is deliberately the shape Kevin's resolution
code has to handle, so it is the right thing to test against — but it also
means the *old* lookup (`ClientId = @client`, else defaults) will treat all
2,144 converted schedules as defaults until the new code is in. Do not run it
against a staging environment that still dispatches with the old code path.

Procedure:

1. Take a fresh export of the staging table (ids differ from production) and
   regenerate: `rationalise_schedules.py staging.csv --scope all --link-table dbo.<KevinsTable>`.
2. Run `rationalise_schedules_staging.sql` with `@Commit = 0`, check the
   safety selects and row counts, then `@Commit = 1`.
3. Test. `restore_schedules_staging.sql` puts back the retired rows, original
   `Name`/`ClientId` on survivors, the zone rows, and removes the link rows
   (matched on `CreatedBy` + `CreatedUtc`). Drop the snapshot tables when done.

Both scripts assume `BulkRunScheduleId` and `BulkZoneSchedule.Id` are identity
columns (`IDENTITY_INSERT`); remove those lines if they are not. The linehaul
dependant check is left commented because the column name on
`tblBulkScheduleLinehaul` is not in this repo.
